## Why

On a screen the accessibility tree does not describe — a LibGDX or other OpenGL game canvas, a camera preview, any custom-drawn surface — the model offers no widget action, only `MODEL_BACK` and `MODEL_MENU`. The shared LLM precondition `LlmGate.allows` (`agent/pipeline/LlmGate.java:52-54`) requires more than two actions, so on those screens the LLM is never consulted, although it is the one component that sees the screen (it receives the screenshot) and the only one with an action that does not need a widget: the off-tree coordinate tap `MODEL_LLM_TAP`. The precondition was written under "two actions or fewer means nothing to decide", which is true for SATA and false for a vision model.

The effect was measured by the Study 03 replication session on campaign E5 (jar `e93dea86`, 60 APKs × 3 prompts × 2 models, 600 s): 12 of 360 tasks have `counters.llm.calls = 0` — `com.serwylo.retrowars_70` and `com.shatteredpixel.shatteredpixeldungeon_896`, every prompt, both models — with zero transport or screenshot errors. The retrowars trace holds one abstract state for the whole task (`AndroidLauncher@…@[W=1][A=2]`) and 399 steps of alternating `MODEL_BACK`/`MODEL_MENU`, all decided by SATA. Across the 163-APK corpus three applications are LibGDX (the two above and `com.serwylo.beatgame_35`); in `e5m1`, 5.9–6.5 % of each arm's steps fall on states the gate closes by size. On those applications the LLM arm is by construction identical to the arm without LLM, which dilutes the E6 contrast symmetrically.

The configuration already carries a seam built for this case and never wired: `ape.llmPercentageNoSubstrate`, the LLM random-routing rate for "a widgetless substrate (Compose, canvas)" (mop-reach-strategies F′). Every campaign arm pushes its `-1` sentinel and rv-android's `tool.py` already maps it (`llm_percentage_no_substrate`). The seam was defined per application from static analysis (`MopData.isWidgetlessSubstrate()`, since deleted); what the evidence calls for is a per-screen fact the explorer knows at run time.

**Revision (2026-09-27).** The first implementation (`f828e5e6`) opened the gate on every opaque step. Campaign E5c showed the mechanism acting as designed and coverage not following (Part A `cov_method` −0.07 pp; only retrowars clearly gains, +4.84 pp): about two thirds of the opaque LLM calls went to screens the model cannot act on — stuck non-cancelable progress dialogs, a text-only dialog, an ad activity, zxing camera previews that take no touch, Compose splash screens. Only the two LibGDX games were dynamic, drawn content. Opaque is not dynamic. On a device (API 30) the difference is visible in the tree APE reads: a game surface is one full-screen leaf `android.view.View` that is focusable and carries no text, while the dialogs are small windows of TextViews and a ProgressBar, the camera surface is absent, and a Compose splash is a chain of non-focusable views under `ComposeView`. The revision keeps the key and the mechanism and narrows the trigger to opaque steps whose tree holds such a **dynamic region**. `evidence.md` records the measurements.

**Second revision (2026-09-27, after the device check and code review).** The device check of the revised gate (task 13) showed every one of shatteredpixeldungeon's 53 answers rejected by the bottom boundary band; a screenshot puts the answered point on the title screen's "Enter the Dungeon" button, a real target wholly inside the band. The band is measured against the display size `Display.getSize()` reports, which already excludes the navigation bar, so on these steps it keeps the model off nothing but the app's own content. The boundary bands are therefore lifted on opaque steps with a dynamic region, and only there. The code review found that the rule's input clause also accepted clickability that `GUITreeBuilder.patchGUITree` writes onto children of a clickable container; the clause now requires native clickability.

## What Changes

- **Opaque screen, defined at run time.** A step's state is *opaque* when it has at least one model action and none requires a target — the state offers only `MODEL_BACK`/`MODEL_MENU`. (An empty action list is excluded: `CoordinateMapper.map` discards any answer on it.) The predicate reads the abstract state only; `dec.opaque` keeps reporting it.
- **Dynamic region, read from the step's tree (revision).** A tree has a dynamic region when, outside any `ComposeView` or `WebView` subtree, it holds a leaf of class `android.view.View` — the class every surface and custom view reports, since none of them overrides `getAccessibilityClassName` — with no text and no content description, focusable, natively clickable or long-clickable (it has an input listener, so it takes touch; clickability APE patches onto a child of a clickable container does not count), covering at least half of the root's bounds. The threshold is a constant, not a plan key. The predicate needs no class list: `GLSurfaceView`, `SurfaceView` and the rest never reach the tree under their own names.
- **Only opaque steps with a dynamic region are routed.** With opaque routing on, the gate opens on a step that is opaque **and** has a dynamic region; `LlmRandom` uses the opaque rate on those steps only. Opaque steps without one (dialogs, cameras, splash and loading screens) stay with SATA, as with the key at `-1`.
- **`ape.llmPercentageNoSubstrate` gets its consumer and keeps its owner.** It stays a sub-parameter of `LLM_RANDOM` with neutral `-1`; no feature is added. **BREAKING (semantics of an unread key):** `-1` changes meaning from "inherit `llmPercentage`" to "opaque routing off"; `>= 0` on a plan carrying `LLM_RANDOM` turns it on. Because the key had no reader and its owner is unchanged, every run under `-1` — which is every existing arm — keeps its gate, its draws **and its plan digest** (its actions too, except on the rare tap answers the parser fix below now recovers): `RunSpec.planValues` already hashes the key on every LLM arm, so moving it to a new feature would have changed the digest even with the mechanism off.
- **`LlmGate.allows` opens on opaque steps with a dynamic region when opaque routing is on**, for all three LLM stages (`LlmNewState`, `LlmStagnation`, `LlmRandom`). The action-buffer conjunct is kept. `LlmRandom` uses the key's value as its rate on those steps and `llmPercentage` elsewhere; a zero rate draws no coin, so `0` means "new-state and stagnation calls only".
- **RNG neutrality when off.** With opaque routing off, the agent generator's draw sequence is identical to jar `e93dea86` under the same seed: the coin stays behind the gate. A permanent test guards it.
- **Off-tree taps as they are.** With no widget on the screen, `CoordinateMapper.map` already turns a `click`/`long_click` answer into an `LlmTapAction`; the prompt, the snap and containment rules and the dead-pair ban do not change.
- **No boundary bands on opaque steps with a dynamic region (second revision).** On a step where opaque routing is on and the step is opaque with a dynamic region, `CoordinateMapper.map` does not apply the `ape.llmBoundaryTopPct`/`ape.llmBoundaryBottomPct` bands and rejects explicitly an answer with either coordinate at `0`: the parser defaults a missing or unreadable coordinate to `0`, and the top band used to catch those answers (`reason:"degenerate"`). The calling stage decides and passes the fact down through `LlmEngine.selectAction`; no plan key is added. At `-1`, and on every other step at any value, the mapper behaves exactly as before.
- **Parser: recover misplaced tap coordinates (second revision).** `ToolCallParser`'s last-resort integer scan also runs when a `click`/`long_click` parses but has no readable `x` or `y` — the case the missing-"y" fix creates from `{"x": {"x": 288, 587}}`, which parsed as `(0,0)` and was discarded. This applies on every LLM arm, `-1` included; it is rare (2 of about 20 000 E5c calls) and marked `repair:"int_scan"`.
- **Telemetry.** Step records carry `dec.opaque:1` when the step's state is opaque and `dec.dyn:1` when the step's tree has a dynamic region (both on every arm, computed whether or not routing is on, omitted otherwise — `dyn` is the predicate's verdict, not a ground truth, and lets the analysis stratify and audit it), and `RUN_END.counters` carries `restarts`, so the effect of off-tree taps on the SATA restart cadence (each new-coordinate tap is a `NEW_ACTION` edge and resets `graphStableCounter`) is measurable.
- **Removed:** the `Config.llmPercentageNoSubstrate` static field and its clamp helper (the plan owns the key), and the INV-RTR-09 "no consumer" seam requirement with its guard test.
- **Documentation:** the `LlmGate.allows` javadoc says "three actions or fewer" while the code blocks two or fewer; it is rewritten to state the new rule.

Declared limitation: the boundary bands of `CoordinateMapper.map` (top 5 %, bottom 6 % of the screen) still apply on every step that is not opaque with a dynamic region, including ordinary screens whose bottom navigation or footer buttons sit in the bottom band (`evidence.md`); measuring the bands against the system bars actually present, on every arm, is a follow-up (`followups.md`) because it would change every LLM arm already measured.

Out of scope: the coordinate mapper's snap/containment rules (on screens where dynamic content shares the screen with widgets the size rule already opens the gate and off-tree taps already exist; no evidence shows taps lost there), `FLAG_INCLUDE_NOT_IMPORTANT_VIEWS` (≈ 2× nodes, changes the abstraction of every arm), a pixel-based state signal for opaque screens (it would change the abstraction, and `LlmNewState` therefore still fires at most once per opaque state), any change to how taps reset `graphStableCounter`, and the campaign rate — a harness choice passed through `tool.py`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `llm-routing`: the shared precondition gains the opaque-dynamic-screen clause (opaque state and dynamic region in the step's tree); probabilistic routing gains the per-step rate choice and the zero-rate no-draw rule; the llmPercentageNoSubstrate seam requirement is replaced by an opaque-screen routing requirement.
- `exploration`: the `LlmNewState` hook requirement restates the shared precondition and its "trivial state" scenario.
- `event-sink`: step records gain `dec.opaque` and `dec.dyn`; `RUN_END.counters` gains `restarts`.
- `llm-infrastructure`: the parser's last-resort coordinate scan also runs on a parseable tap action without readable coordinates.

## Impact

- **Jar code:** `agent/pipeline/LlmGate.java` (opaque and dynamic-region predicates), `LlmNewStateStage.java`, `LlmStagnationStage.java`, `LlmRandomStage.java` (each passes the edge-band decision to the engine), `DecisionPipeline.java` (derives opaque routing and injects the flag and rate at assembly); `llm/LlmEngine.java` and `llm/CoordinateMapper.java` (the edge-band parameter and the explicit degenerate rejection); `llm/ToolCallParser.java` (the extended last-resort scan); `utils/Config.java` (field and clamp deleted); `runtime/` unchanged; `telemetry/StepRecord`/`NdjsonSink`/`RunCounters` and the agent site that opens a step record; `agent/ApeAgent.requestRestart` (restart count).
- **Tests:** gate/stage tests over real compressed trees captured on a device (fixtures under `src/test/resources`, read through the jar's XML reader and `patchGUITree`), `CoordinateMapper` tests (every call gains the edge-band argument; new cases for the lifted bands and the degenerate rejection), the engine test doubles, `LlmRandomStageTest` (the INV-RTR-09 no-consumer test is replaced), `ConfigTest` (clamp test removed), `RunSpecResolveTest` (a golden digest for the `llm`/`llm_mop` presets at `-1`), new gate/neutrality tests.
- **Presets:** unchanged — every preset keeps `ape.llmPercentageNoSubstrate=-1`.
- **rv-android (`aperv-tool`):** no code change; `tool.py:198` already maps the key, and the key's type (`DOUBLE`) and declared default (`-1.0`) that `tests/migration/test_jar_tables.py:86-87` pins are unchanged, as is its `inert` status on a non-LLM plan (`tests/test_runspec.py:65`). `openspec/specs/aperv/spec.md:760` ("`LLM_RANDOM` sub-parameter") stays correct; only the description of `-1` needs a follow-up there. An arm that wants the mechanism sets `llm_percentage_no_substrate >= 0`.
- **Studies:** E5 data is untouched. At `-1` the new jar equals `e93dea86` in plan digest and decisions, apart from the rare tap answers the parser now recovers instead of discarding (marked `repair:"int_scan"`), so E5b (on `e93dea86`) can select the configuration E6 runs on the new jar; E5c compared `-1` with a positive value on `f828e5e6`. The revised jar keeps the plan digest at every value of the key (the threshold is a constant), so a positive value resolves to the same digest on `f828e5e6` and on the revised jar while the behavior differs: `RUN_START`'s build stamp (`GIT_SHA`) is what tells them apart. E5c's order confound (arms always run off-then-on) is recorded in `followups.md` for the next in-loop experiment. The revised jar's commit and sha256 are handed to the Study 03 session once built.
