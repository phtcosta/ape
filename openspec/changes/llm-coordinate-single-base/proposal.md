## Why

The LLM arm uses the [0,1000) coordinate space in three places, and they disagree about what 1000 means. The element list in the prompt divides a widget's centre by the right and bottom edges of the **active window's root node**. The action history, in the same prompt, divides by the **display** (`Display.getSize`), and does not clamp the result to [0,999]. The model's answer is turned back into a pixel by multiplying by the display, the same rectangle the screenshot is captured at. An answer the model reads off the image lands where the model meant. An answer it **copies from the element list** lands somewhere else.

The bases differ on almost every screen of the campaign emulator, in two ways:

- **Full-screen activity windows.** The DecorView extends behind the navigation bar, so the root's raw bounds end at y=1920. The display reports 1794. A copied coordinate lands above the widget's centre by 6.56 % (1 − 1794/1920) of the centre's distance from the top of the screen: about 12 px near the top, about 106 px near the bottom.
- **Dialogs, popups, and windows the keyboard resized.** The root is the window itself, e.g. `[28,690][1052,1166]`. The list then divides by 1052 × 1166. Both axes are off, and the error reaches hundreds of pixels: a widget `[745,1040][897,1140]`, centred at `(821,1090)`, is listed as `@(780,934)`, and a copy is tapped at `(842,1675)`, 585 px below it.

**The boundary band has the same root cause.** `CoordinateMapper` rejects an answer whose pixel y is greater than `0.94 × deviceHeight` or less than `0.05 × deviceHeight`. The gh6 design (`openspec/changes/archive/2026-03-17-gh6-aperv-llm-integration/design.md:294`) wrote the bottom band as "navigation bar (bottom 6% of screen)", a fraction that only holds on a 1920-high screen (126/1920 = 6.56 %). At runtime `deviceHeight` is the display, 1794, which already excludes the navigation bar. The band therefore rejects y ∈ (1686, 1794): app content, where 32.8 % of E6 states have a target (bottom-navigation items, `next`/`settings` buttons, snackbar actions). The defect's upward shift kept copied answers out of that band. Fixing the list alone moves copies of bottom widgets back into it.

The defects date from `b2852ddf` (gh6, 2026-03-17). That change's design (`:277`) planned one base for the prompt and the answer. The router read the display under a comment saying "same as ApePromptBuilder", while the builder read the root. `llm-tap-display-bounds` (2026-07-21) moved the off-tree tap's validity domain to the display, but kept the root as correct for node actions and did not touch the prompt or the bands. `llm-native-toolcall-repair` (J1b, 2026-07-23) exposed the bands as keys whose defaults reproduce the hard-coded values, and did not revisit what they were fractions of.

**Measured effect.**

- **Settings audit.** The Study 03 settings audit (`rvsec-study03-replication-package/experiments/E6-campaign/settings-audit.md` §4, script `settings-audit/coordinate_base.py`) quantified the list defect on E6 arm 4 (jar `e93dea86`, 130,986 LLM decisions):
  - 41.1 % of answers are copied from the list.
  - Decisions sent to a different target than the model chose: lower bound 1.3 %, central estimate 4.1 %, ceiling 6.0 %. For E5b v13_A, the arm E6 inherits, the figures are 2.3 % / 7.1 % / 9.3 %.
- **Counterfactual replay.** A replay of the mapper over the same traces (`evidence/coordinate_counterfactual.py`, 2026-10-05) reproduces every recorded outcome: 130,199 of 130,199 aligned calls. Holding the model's choice of list entry fixed (the same-entry assumption), the share of copied answers that map to the widget they name is shown below. A mapped answer is either executed or refused by the dead-pair ban, so the table has two columns per study: all mapped answers, and the live ones, which execute.

  | Scenario | E6 mapped (53,352 copies) | E6 live | E5b mapped (4,106 copies) | E5b live | Copies rejected at the boundary (E6) |
  |---|---|---|---|---|---|
  | As run | 70.8 % | 35.5 % | 69.9 % | 54.3 % | 1.0 % |
  | Display base only, bands unchanged | 83.6 % | 46.0 % | 85.3 % | 68.2 % | 4.1 % |
  | Display base with the bands re-derived | 87.2 % | 48.8 % | 89.4 % | 72.1 % | 0.1 % |
  | The same, listing each widget at the centre of its visible part (this change) | 87.1 % | 48.8 % | 89.4 % | 72.1 % | 0.1 % |

  - **The live column is the one that changes what runs.** In E6 it gains 7,085 executed hits (18,943 → 26,028), 5.4 % of the 130,199 aligned calls. The mapped column counts 20,450 hits that the ban refuses under this change.
  - **The replay holds the strike record fixed.** Strikes are replayed from the recorded run, but with the fix the intended widgets would be executed, and would collect strikes, more often (see Risks in `design.md`). As run, the ban refused 18,837 of the 37,780 copies that mapped to their widget (49.9 %). If the same share held under the change, the live gain would be about 4,400 rather than 7,085. The live gain therefore lies roughly between 3.3 % and 5.4 % of decisions, under the same-entry assumption.
  - **What this does to exploration can only be estimated roughly offline.** As run, an executed copy reached a new state 8.7 % of the time when it hit its widget, 6.2 % when it hit another one, and 3.2 % as an off-tree tap (`evidence/curation_e6.out` §D, clickable copies). Weighted by these rates, the outcome changes of the copies from as run to this change (`evidence/coordinate_counterfactual.out` §8) come to about 370 more new-state steps over the 162 E6 runs with the strike record held fixed, or about 310 if a refused answer's step is credited with a SATA step's 2.0 % new-state rate (`curation_e6.out` §D, last line). Scaled to the as-run refusal share, as above, that is about 190 to 230. In all cases it is about one to two and a half per run (1.2 to 2.3). The rates are confounded: copies that hit as run are concentrated where the defect did not bite. Only a run on the device measures it. The effect on misuses is not estimable offline.
  - In dialogs and popups, copies map to the named widget 21.0 % of the time as run and 97.4 % with this change.
  - Beyond copies, the bottom band also rejects 4,879 E6 answers that are not list copies (3.7 % of all answers). The list fix does not move these. With this change, 2,995 of them land on a tree widget and 1,865 become off-tree taps. The other 19 have `qwen` y ≥ 1000 and stay rejected (D8). These figures come from the replay without the bottom band; the 19 are its 12 matches and 7 taps at the clamped edge.

**Scope.** Any fix changes what the LLM arm measures. It applies to future studies only, and E6 will not be re-run. The defect enters the Study 03 paper as one found in the analysis of the results. Its effect on decisions is measured; its effect on misuses is not, and is never stated as null (author's decision, `rvsec-study03-replication-package/HISTORY.md:693-697`, 2026-10-03, which reverses the same day's decision to keep it out).

**Relation to Study 03.** Study 03 fixed the model (`Qwen/Qwen3-VL-4B-Instruct-FP8`), the engine (vLLM v0.29.0), the prompt variant (`v13`), greedy sampling and the dose (0.9), and it fixed them as the behavior of one binary: jar `e93dea86` (sha256 `4e3808c7…`), which E5, E5b and E6 all ran. Its selections transfer from E5b to E6 because the jar is the same, and its E6 decision selects nothing for a later experiment (`rvsec-study03-replication-package/openspec/changes/archive/2026-10-02-e6-campaign/decision.md:284-286`). Nothing in Study 03 forbids changing the jar afterwards; its settings audit already classifies this repair as one that "changes what the LLM arm measures, so it applies to future studies only" (`rvsec-study03-replication-package/experiments/E6-campaign/settings-audit.md:327-331`). But no study can re-calibrate the prompt in the time left, so an arm run with this jar uses a model, a variant and a sampling that were chosen in-loop on the defective rendering. `v13` itself was kept as the incumbent, not as a winner: in E5b, `compact_v1` and `v17` were indistinguishable from it (`rvsec-study03-replication-package/openspec/changes/archive/2026-09-28-e5b-inloop/decision.md:22-24,87-94`).

On 2026-10-07 the author decided how far the change goes under that constraint:

- **Defect repairs are in**, in the list and in the history alike: the coordinate base (D1), the visible centre (D11), the band (D7, D8), the history's coordinates (D5), its `@(0,0)` entries (D9), its outcomes (D12), and its class and text (D13). One clause of the `v13` system message goes too, because it asks for visit counts the `v13` prompt never shows (D14). Each one corrects something the prompt shows that is false, or that the spec has always said otherwise.
- **Improvements wait** in `pending.md`, outside the binding scope, until the author confirms them one by one. Each is a prompt change that repairs nothing, and each widens the distance from the prompt Study 03 calibrated. The author confirmed one the same day: one line per widget without an ordinal in the `v13`/`v17` lists (P1, design D10), because a list that shows the same widget twice has no reason to stay. Two remain pending: the `id=` step in the history's identifier (P2), and a `type_text` entry naming its field (P3).

The defect went unnoticed for three reasons:

- `ApePromptBuilderTest` always calls `build(null, …)`, so the root read never runs. `ApePromptBuilderIdentifierTest` passes real actions with a null tree and asserts only that a coordinate is present (`@(`), never its value.
- `PromptIntegrationTest` re-implements the normalization formula in the test instead of calling production code.
- `ScreenshotStep.deviceDimensions` and the history normalization in `StatefulAgent` have no tests. The `llm-prompt` spec writes `deviceWidth`/`deviceHeight` without naming their source and asserts "the SAME coordinate space the LLM responds in". Nothing checks that assertion. The band scenarios in `llm-routing` are written against a 1080 × 1920 device that the jar never sees at runtime.

### Part B: MOP guidance by static distance and handler stamp (added 2026-10-07, evening)

The MOP arm guides exploration with a yes/no mark per widget: +500 when the static analysis says the widget's handler calls a monitored operation directly, +300 when it reaches one through other methods. Three facts measured on Study 03 make that mark weak (rv-android `docs/20261005_verificacao_plano_gator_compose.md` §3 table, untracked in rv-android): reachability saturates (41 % of handlers reach a target, and on the median screen 67 % of the widgets are marked), one handler is attributed to many widgets (68.3 % of handlers sit in four keys or more), and 58.6 % of clicked nodes have no resource id, so the `(activity, resource-id, event)` key matches nothing (97.4 % in Compose-only apps). Two changes in rv-android, finished today, produce what a better guide needs: gh120 (archived `c9a43d98`) gives every app method its call-graph distance to each monitored target and to the app→library boundary, and gh121 (`b7abcd6a`) makes the instrumented app write each widget's handler class on its accessibility node. Both name a consumer change in this repository as the place where the wire format, the reading and the scoring are decided (gh120 design `:86-87`, gh121 proposal `:25`). The author decided on 2026-10-07 that this change is that consumer.

## What Changes

- **One base, carried from one source.** The `{width, height}` that `ScreenshotStep.deviceDimensions` returns is already used to capture the screenshot and to map the answer. It becomes the only base for the element list and the action history too. `LlmEngine` passes it to `ApePromptBuilder.build`. The builder no longer reads the tree's root node for dimensions. The `GUITree` parameter is removed from `build`, because dimensions were its only use (SDD-P3).
- **One normalization primitive.** `CoordinateNormalizer` gains the forward direction, pixel → [0,1000), next to the existing inverse `normalize`. These copies are deleted, and every [0,1000) value the prompt shows comes from that one primitive:
  - the inline copies in `ApePromptBuilder`: the shared line formatter used by `ape_current`, `ape_reasoning` and `compact_v1`, and the `v13` and `v17` list builders;
  - the history computation in `StatefulAgent.recordActionHistory`.
- **History carries pixels, the builder normalizes.**
  - `ActionHistoryEntry` stores the executed widget's pixel bounds instead of a pre-normalized pair. The same widget gets the same `@(x,y)` in the list and in the history of one prompt, by construction.
  - The history also stops showing coordinates outside the answer space. `StatefulAgent.recordActionHistory` divides the widget's whole centre by the display and does not clamp (`StatefulAgent.java:1836-1837`), so a widget centred below the display is shown at y ≥ 1000, and one centred left of or above it at a negative value. E6 arm-4 prompts carry 2,860 such entries, in 2,182 prompts (1.7 %); E5b `v13_A`, 134 in 111. Ten of the 19 E6 answers with `qwen` y ≥ 1000 copy one of them (`evidence/prompt_zero_scan_e6.out`). Rendered at the centre of the visible part, a history entry is always inside [0,999] or carries no coordinate.
  - Every history renderer goes through `formatHistoryEntry`: the default branch, `v13`, `visual_only`, and `v17`, whose compact `Recent:` line was rendered inline from the raw fields.
  - `StatefulAgent` stops calling `AndroidDevice.getDisplayBounds()` for the prompt.
- **History entries for actions without a resolved node say what ran.** Today an off-tree `MODEL_LLM_TAP` and a `MODEL_MENU` are both recorded as `click @(0,0)` with no class. Such an entry appears in 24.2 % of E6 arm-4 prompts (31,466 of 130,266) and 22.5 % of E5b `v13_A` prompts (2,157 of 9,586).
  - An LLM tap now records its own pixel and its `long_click` flag.
  - A menu press records `menu`, rendered without coordinates, as `back` already is.
  - `v17` no longer renders `back@(0,0)`.
  - `ActionHistoryEntry` is also specified in `exploration` ("StatefulAgent — Action History Ring Buffer"), whose field table changes with it.
- **Each history entry carries its own action's outcome.** `recordActionHistory` runs when the next action is selected, and it stored in that action's entry the comparison of the current screen with the previous one, which is the outcome of the action before (`StatefulAgent.java:828-829, 850-853, 1848-1854`). No later step corrected it, so every entry showed its predecessor's `→ same` / `→ new screen` / `→ previous screen`, and the newest action's own outcome appeared in no prompt. The comparison is kept and moved: the entry is appended without a result, and the next state update fills it before any LLM stage runs (design D12). The `exploration` requirement has described the correct behavior since gh6; the code never followed it.
- **A history entry names its widget as the list does.** The `exploration` field table has always said that `widgetClass` is the class simple name and `widgetText` the text or content-description. The code stores the full class name and the text only (`StatefulAgent.java:1825-1826`). In E6 arm 4 every node-action entry (555,981) showed the full name, in 98.9 % of prompts; in at least 11.4 % of prompts an entry showed no text for a widget that the same prompt's list labelled (`evidence/history_fields_e6.out`; E5b: 98.8 % and 10.6 %). `recordActionHistory` now calls the list's own helpers, made public and static: `simpleClassName`, and `textOrContentDescription`, the first two steps of the list's identifier. The list's `id=<shortId>` step is not applied (`pending.md` P2). Design D13.
- **A list line with no resolved node omits its coordinate.** The main spec has required this since gh6 ("Unresolved action node"), but the three list sites write `@(0,0)` instead, and no test covers it. They now omit `@(x,y)`. No E6 or E5b prompt contains such a line, so the repair changes no measured prompt.
- **A widget is listed at the centre of its visible part.** The list used the centre of the node's whole bounds, clamped to the display edge. The jar taps a node action at the centre of the node's part inside the visible window, and drops the action when nothing is visible (`exploration` "Off-Screen Action Handling"; the code labels the drop INV-EXPL-19). The list now shows that point: the bounds intersected with the display, then the centre. A widget entirely off screen keeps its line with no `@(x,y)`, like an unresolved node; whether to list it at all stays the open curation question.
  - In E6, 21,938 list lines (2.0 %, in 3.6 % of prompts) belong to a node entirely off screen, and 58,765 (5.3 %) to a node cut by the display edge. Another 1,142 belong to a zero-height node inside the display. `Rect.intersect` accepts such a node, so it keeps its coordinate (`evidence/dup_identity_e6.out`).
  - 227 copied answers copied an entry with no visible area: 200 nodes entirely off screen and 27 zero-height nodes. As run, the boundary bands rejected 191 of them: the bottom band 174, the top band 17 (nodes above the display). Under the display base with the re-derived band but the clamped centre (scenario S3), they would hit another widget (103), tap off-tree at the edge (83), hit the top band (17), or snap to a node the dispatcher then drops (24).
  - Copies mapping to their widget: 87.1 % against 87.2 % with the clamped centre, the difference being those 24 snaps and one edge-cut copy (`evidence/coordinate_counterfactual.out`, S3 versus S4). E5b is unchanged.
- **The boundary band is re-derived in the display base.**
  - **BREAKING (configuration):** `ape.llmBoundaryBottomPct` is retired. On the display base every pixel below 1794 is app content, and an answer cannot reach y ≥ 1794 (`normalize` clamps). Any value below 1.0 therefore rejects app content, and any value from 1.0 up never fires. A properties file that still sets the key aborts resolution with a reason naming this change.
  - `ape.llmBoundaryTopPct` changes its default from `0.05` to `0.035`. That is the status bar, 63 px on the campaign AVD (`statusBarBackground [0,0][1080,63]` in 210 UIAutomator dumps), divided by 1794. It still rejects a degenerate `(0,0)`. It stops rejecting y ∈ [63, 90), which is the top of the app's toolbar.
  - An answer outside [0,999] on either axis is rejected as `boundary` before it is mapped, for every tool except `back`; its clamped pixel is computed for telemetry only. Today 19 such E6 answers were rejected only because `normalize` clamped them into the bottom band. Ten of them copied an out-of-space history coordinate that the jar itself printed, which this change stops printing; the other 9 pointed past the image on their own. Without the band, the clamp would turn them into actions at the screen's edge: 12 matches and 7 off-tree taps in the replay.
- **The `v13` system message stops ranking by visits.** It reads `PRIORITY: [DM]/[M] elements > navigation to new screens > unvisited elements > visited elements.`, but the `v13` list shows no visit count, unlike the other variants (`(v:N)` in the default branch, status tags in `v17`). The clause `> unvisited elements > visited elements` is removed and nothing replaces it. Every `v13` call is affected. Design D14.
- **The `v13` and `v17` element lists show each widget once, with no ordinal** (an improvement, confirmed by the author on 2026-10-07; `pending.md` P1). Both lists write one line per target-requiring **action**, numbered `1.`, `2.`, …. A widget with several actions (click and long-click, two scroll directions) therefore appears as several lines. Each line carries only per-widget content (class, identifier, coordinate, MOP marker, static metadata), so the copies are identical apart from the number. In E6:
  - 25.3 % of list lines share their node's bounds with an earlier line, and 74.2 % of prompts contain at least one such repeat. 274,830 lines (24.9 %) also share the earlier line's target `Name` and collapse; the other 4,633 are distinct `Name`s with identical bounds (a container and its single child) and stay (`evidence/dup_identity_e6.out`).
  - The number is read by nothing: no tool, the parser and the mapper all ignore it. The answer is a coordinate, and the mapper matches it against the state's actions, never against list lines.
  - The list therefore becomes one line per widget, in order of first appearance, with no ordinal prefix. A widget is the pair (target `Name`, resolved-node bounds), not the node's identity: two alias nodes with one `Name` and one rectangle show the same line and the same `@(x,y)`, and the trace records the pair for every listed action, so offline analyses can rebuild each line, up to a `Name.toString` collision between two namers (design D10). `v17`'s status tag counts the visits of all the widget's actions, and its screen-info line counts widgets on both sides of its ratio (`N/M elements tested`).
  - The `ape_current`, `ape_reasoning` and `compact_v1` lists keep one line per action and their `[<index>]` prefix.
  - `ModelAction`s, the mapper, SATA and the exploration model are untouched: they never read the prompt text.
- **BREAKING (experimental comparability):** prompts and routing differ from E5b and E6.
  - The list's coordinates change on every screen where the root and the display disagree, which on the campaign emulator is nearly every screen.
  - The boundary decisions change for answers in the old bottom band and in y ∈ [63, 90).
  - The `v13`/`v17` lists lose their ordinals and their repeated lines.
  - Every node-action history entry shows the class simple name, and the content-description where the widget has no text.
  - The `v13` system message no longer ranks unvisited above visited elements.
  - Widgets cut by the display edge are listed at a different point, and wholly off-screen ones without a coordinate.
  - Every history entry's `→ <result>` now describes its own action rather than the one before.
  - Prompts are not byte-comparable with E5b/E6, and an arm run with this jar is a new arm version, not a re-run of the inherited one.

Not changed:
- the system message, apart from the `v13` `PRIORITY` line (D14);
- the variants' layouts, apart from the `v13`/`v17` element lists (one line per widget, no ordinal), the `v17` screen-info line (counted in widgets), the `v17` history entry, the history entries of LLM taps and menu presses, the omission of `@(x,y)` for an unresolved or wholly off-screen node, and the listed point of a widget cut by the display edge;
- the screenshot path;
- containment, snap tolerance and off-tree tap synthesis in `CoordinateMapper`;
- the off-tree tap validity domain;
- node-action dispatch;
- the `no_match` reason set (`degenerate`, `boundary`, `dead_pair`).

### Part B: MOP guidance

- **Format 2 of the compact MOP artifact** (contract here, generator in rv-android under its own Fast-Forward change `gh122`, which amends the `aperv` spec through a delta): the number of targets, per widget and event the K = 3 nearest targets as `[[i, d], …]`, the same per activity, and a table from handler class to flags and distances. INV-DRV-06 is amended to allow integer indices, distances and class names, still no signature. The A′ source 3 of `mopActivitiesAugmented` leaves out an activity's own `<init>`/`<clinit>`, as `activityDist` does (author's decision). The jar reads only format 2 (INV-MOP-34 here; `FORMAT_VERSION` and the `aperv` spec's `formatVersion` on the rv-android side). Design D15.
- **The tree keeps the handler stamp.** `GUITreeBuilder.fillNode` copies `rvsec.click`/`rvsec.longClick` from the node's extras. D16.
- **One MOP lookup per (node, event)**: the stamp's class when the table lists it, else the id key as today. Scoring, the shortcut, the prompt marker, the `MOP NAVIGATION` count, the state MOP density and retirement all use it; the launcher reads the per-activity `activityDist`, not the lookup. D17.
- **Two scoring modes**, by the new key `ape.mopScoring`: `flag` (default; the E6 mark, +500/+300) or `distance` (500/400/300 for a nearest unretired target at d ≤ 1 / 2 / 3, 0 beyond; the weight is split among the actions tied at the state's best weight level, with a floor at the next level's weight; the shortcut ranks by the weight before the split). Values from the plan's decision 10, which the author adopted; the plan gives 0 only beyond D_max = 6, and 0 for d = 4–6 is the author's decision of 2026-10-08. D18.
- **Targets retire** under `distance`: the first interaction of a widget in its activity counts against the targets of the lookup that gave its weight (with containment), and a target counted 3 times (`ape.mopRetireAfter`) stops attracting. D19.
- **The launcher orders activities** by their nearest unretired target under `distance`, instead of round-robin in manifest order. D20.
- **The MOP shortcut tries widgets new to the activity first** (plan decision 9), then the boost, in both modes. D21.
- **The prompt marker is the scoring's verdict for the line**: `[DM]`/`[M]` exactly when the score treats one of the line's actions as direct/MOP under the active mode. This fixes the three disagreements of review R9 and changes the `v13` prompt beyond Part A even under `flag`. D22.
- **Telemetry**: `dec.mopd`, `dec.mops`, `dec.ret`, and counts in `MOP_DATA` and `RUN_END`. D23.
- **BREAKING (artifact):** a format-1 `.mop.json` is rejected and a MOP arm aborts. Every MOP run needs an artifact derived from a gh120 `.apk.json`. Nothing in the derive or the jar enforces that (gh120 decided against a guard, D9; the author, 2026-10-08, against one in the jar): a September `.apk.json` derives to a format-2 artifact with `targets: 0`, which runs without distance data and shows `MOP_DATA.targets: 0`; only the corpus hand-off keeps it out.
- **BREAKING (experimental comparability):** the MOP arms change even under `flag` (shortcut order, marker, stamp lookup on a stamped APK). The E6 arms are reproduced by jar `e93dea86`.
