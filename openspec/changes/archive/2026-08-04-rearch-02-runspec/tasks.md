## 8. Device smoke — descoped to a coordinated end-to-end run

**This group carries no tasks. Owner decision, 2026-08-04: the stage-2 device smoke is skipped**, and the validation it would have performed is folded into a **single coordinated end-to-end run once every planned change on both sides has landed** — the seven `ape` re-architecture stages and the five `rvsec` counterparts (`gh93`…`gh97`). The reason, recorded as given: the Python side is still being implemented, so a stage-2 device smoke would validate a moving jar against a moving harness, and each later stage would overwrite the jar it installed anyway. The two tasks that stood here (a `sata_mop_widget` platform run, and the fail-fast aborts) are removed rather than ticked — they were not performed, and a tick would say they were.

**What is deferred, enumerated so the obligation survives without reading this change's history.** Four things, none of which the JVM suite can reach:

1. **The abort composition.** `RunSpecAbortTest` covers `RunSpec.resolve`, but composing the diagnostic and exiting nonzero lives in `Monkey.run` and needs a device (task 3.4). Concretely: a properties file carrying one unknown key exits nonzero with `[APE-RUNSPEC-ABORT]` and injects **zero** events, and `--ape bfs` aborts naming the valid agent set `{sata, random, replay}`.
2. **The runtime emission order.** That `RUN_START` precedes every `[APE-*]` line in a real trace. The JVM guard is a source-order guard over `Monkey.java` only (task 4.4) — it catches a refactor that moves the echo, not a runtime reordering.
3. **The after-state of a real run.** No `sataModel.obj` / `sataGraph.*` in the output directory (group 5 deleted the persistence protocol), and the coverage dump preceding the `action-history` output (INV-COV-10's restated boundary).
4. **The end-to-end run of the five arms** — the four campaign arms and `ape_pure` — against a post-stage-2 jar (task 6.4's deferred half).

**The deployment gate moves with them, and its constraint is unchanged.** This section used to host D-4's binding event, because installing the jar under test into `aperv-tool` (`mvn install` → `copy-jar-to-aperv-tool`) was the first act of the stage to put a post-stage-2 jar in front of a device. With the smoke descoped, **no task of this change installs the jar at all**: stage 2 is wholly jar-side plus one Python edit, and it deploys nothing. The condition therefore holds vacuously across the whole stage, and the binding event sits outside this change, at the first `mvn install` of a post-stage-2 jar — which is now the coordinated run. The owner decision of 2026-08-04 stands verbatim: *the `rearch-counterparts` → `modules` merge SHALL precede the first `mvn install` of a post-stage-2 jar.* It also holds in fact today: the rv-android tree runs from `rearch-counterparts`, which carries the removal (`grep -n ape_pure_mode tool.py` returns nothing; `tool.py` sha256 `aba920ea68f17bb4ea0c346a48bc4a1f63f7a2cc67df7a80df0f32e3d0c93ae8`). Whoever runs the coordinated smoke must verify the checkout immediately before installing (`git -C <ws>/rvsec branch --show-current`) rather than trusting this note — a tree switched to `modules` does not carry the removal, and every campaign arm would abort before step 1.

The coordinated run itself is tracked in `docs/plans/20260802_rearchitecture_roadmap.md`, which is the instrument that coordinates both repositories; it is not a task of this change. Rationale and cost: design **D-13**.
